# 負の値を導入する計算ロジックの提案

## 調査結果サマリー

### 1. 公式・有名サービスでの調査結果

**公式・有名サービスでは負の値を使用していない**
- ポケモン公式：タイプ相性は0, 0.5, 1, 2, 4倍の正の値のみ
- ポケモンショーダウン：公式の計算式に基づき、負の値は使用していない
- ポケマス（ポケモン徹底攻略）：公式のダメージ計算式を踏襲、負の値なし
- Pikalytics：パーティ評価ツールだが、負の値の使用は確認できず

### 2. その他のサービスでの調査結果

**非公式ツールでも負の値の使用例は見つからなかった**
- 相性補完チェッカー：タイプ相性を数値化しているが、負の値は使用していない
- 各種ファンメイド計算ツール：公式の計算式に基づいている

### 3. 既存サービスの計算ロジック

**共通する計算方法：**
1. **タイプ相性の倍率計算**：攻撃技のタイプ × 防御側ポケモンのタイプ = 倍率（0, 0.5, 1, 2, 4）
2. **複合タイプの計算**：タイプ1の倍率 × タイプ2の倍率 = 最終倍率
3. **パーティ全体の評価**：各ポケモンの弱点倍率を合計して表示

**評価方法：**
- 弱点が多いタイプを「リスクが高い」として表示
- 耐性（0.5倍、0.25倍）も正の値として扱い、合計値が小さいほど「安全」
- ただし、耐性の効果を明確に可視化していないサービスが多い

## このサービスに活かせる点

### 1. 耐性の可視化の改善

**現状の問題点：**
- 耐性（0.5倍、0.25倍）も正の値として合計しているため、耐性の効果が弱く見える
- 例：パーティに「みず」タイプが1匹いる場合、「ほのお」タイプの攻撃に対して0.5倍だが、合計値は0.5となり、弱点（2倍）と比較して効果が分かりにくい

**改善案：**
- 耐性を負の値として扱うことで、弱点と耐性を明確に区別
- 弱点は正の値、耐性は負の値として合計し、最終的な「リスクスコア」を算出

### 2. バランス評価の精度向上

**提案する計算ロジック：**

#### 方式A: 弱点と耐性を分離して評価

```
リスクスコア = 弱点の合計 - 耐性の合計

例：
- 「ほのお」タイプの攻撃に対して
  - 弱点（2倍）のポケモンが1匹 → +2.0
  - 耐性（0.5倍）のポケモンが1匹 → -0.5（負の値として扱う）
  - リスクスコア = 2.0 - 0.5 = 1.5
```

**メリット：**
- 弱点と耐性の効果が明確に区別される
- パーティに耐性ポケモンがいる場合、リスクが相殺されることが視覚的に分かる

**デメリット：**
- 負の値が表示される可能性がある（例：リスクスコア = -1.0）
- 色のグラデーション設計が複雑になる（負の値から正の値まで）

#### 方式B: 弱点と耐性を相対評価

```
リスクスコア = 弱点の合計 - (耐性の合計 × 重み係数)

重み係数 = 2.0（耐性の効果を強調）

例：
- 「ほのお」タイプの攻撃に対して
  - 弱点（2倍）のポケモンが1匹 → +2.0
  - 耐性（0.5倍）のポケモンが1匹 → -0.5 × 2.0 = -1.0
  - リスクスコア = 2.0 - 1.0 = 1.0
```

**メリット：**
- 耐性の効果を強調できる
- リスクスコアが負になる可能性を減らせる

**デメリット：**
- 重み係数の調整が必要
- 計算が複雑になる

#### 方式C: 弱点と耐性を別々に表示（推奨）

```
弱点スコア = 弱点の合計（2倍以上の倍率のみ）
耐性スコア = 耐性の合計（0.5倍以下の倍率のみ、負の値として表示）

最終リスク = 弱点スコア + 耐性スコア

例：
- 「ほのお」タイプの攻撃に対して
  - 弱点（2倍）のポケモンが1匹 → 弱点スコア = +2.0
  - 耐性（0.5倍）のポケモンが1匹 → 耐性スコア = -0.5
  - 最終リスク = 2.0 + (-0.5) = 1.5
```

**メリット：**
- 弱点と耐性の効果が明確に分かる
- 計算がシンプル
- 既存のUIとの親和性が高い

**デメリット：**
- 負の値が表示される可能性がある

### 3. 色のグラデーションの改善

**負の値を導入する場合の色設計：**

```
リスクスコア < 0（耐性が優勢）:
  - 色：青系（例：rgb(200, 220, 255)）
  - 意味：このタイプに対しては耐性がある

リスクスコア = 0（バランス）:
  - 色：白（rgb(255, 255, 255)）
  - 意味：弱点も耐性もない、または相殺されている

リスクスコア > 0（弱点が優勢）:
  - 色：白から赤へのグラデーション（既存の実装）
  - 意味：このタイプに対しては弱点がある
```

**実装例：**
```typescript
function getColorForValue(value: number, minValue: number, maxValue: number): string {
  if (value < 0) {
    // 負の値（耐性が優勢）: 青系
    const normalized = Math.abs(value) / Math.abs(minValue);
    const r = Math.round(200 + (255 - 200) * (1 - normalized));
    const g = Math.round(220 + (255 - 220) * (1 - normalized));
    const b = 255;
    return `rgb(${r}, ${g}, ${b})`;
  } else if (value === 0) {
    // ゼロ（バランス）: 白
    return `rgb(255, 255, 255)`;
  } else {
    // 正の値（弱点が優勢）: 白から赤へのグラデーション
    const normalized = (value - 0) / (maxValue - 0);
    const r = Math.round(255 + (220 - 255) * normalized);
    const g = Math.round(255 + (38 - 255) * normalized);
    const b = Math.round(255 + (38 - 255) * normalized);
    return `rgb(${r}, ${g}, ${b})`;
  }
}
```

## 推奨実装方式

**方式C（弱点と耐性を別々に表示）を推奨**

**理由：**
1. 計算がシンプルで理解しやすい
2. 既存のUIとの親和性が高い
3. 弱点と耐性の効果が明確に分かる
4. パーティ構築の意思決定に役立つ

**実装の流れ：**
1. `calculateSingleTypeEffectiveness`関数は変更不要（0.5, 1, 2, 4倍を返す）
2. `calculatePartyWeaknesses`関数を修正：
   - 各ポケモンの倍率を計算
   - 倍率が1.0より大きい場合 → 弱点スコアに加算
   - 倍率が1.0より小さい場合 → 耐性スコアに加算（負の値として）
   - 最終リスク = 弱点スコア + 耐性スコア
3. `getColorForValue`関数を修正：
   - 負の値の場合は青系の色を返す
   - 正の値の場合は既存の白から赤へのグラデーション

## 注意点

1. **ユーザーへの説明が必要**：負の値の意味を明確に説明する必要がある
2. **色の設計**：負の値（青）と正の値（赤）の両方が分かりやすい色設計が必要
3. **計算ロジックの透明性**：どのように計算されているかを「弱点計算について」で説明する必要がある
